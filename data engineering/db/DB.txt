->DataBase: Collection of data.
->DBMS: Application that manages data. Eg: MySQL.
-Page:
	-A DB page is I/O unit created and managed by the database s/w itself.
	-Entire page is fetched into memory for any read or write.
	->A rows unique address is composite key(DB Page ID+It's position in the page).
-WAL:
	-When modifying data in DB changing data in memory the flushing to disk is risky, as memory is volatile if machine crashes before flush changes are gone.
	-WAL is separate, append only structure on disk that records every change as it happens.
		-This is faster because appending to a log is cheaper than scattered page writes.
		-WAL is written to disk first before actual disk change or commit ok is sent back.

->Window function call always contain over clause directly following the window function.
	-Eg: select depname, sal, avg(sal) over (partition by depname) from empsal;
	-Eg: select sal, depname, rank() over (partition by depname order by sal desc) from empsal;
	===WindowFrame: Many (but not all) window functions act only on the rows of the window frame(like sum(col1) over(order by col2 partition by col3)), rather than of the whole partition.
		-Check syntax ROWS BETWEEN UNBOUNDED PRECEEDING AND CURRENT ROW.
		-ORDER BY is supplied then the frame consists of all rows from the start of the partition up through the current row, plus any following rows that are equal to the current row.
		-SELECT salary, sum(salary) OVER () FROM empsalary; #Here lack of order by and partition by makes all rows as single frame.
		-SELECT salary, sum(salary) OVER (ORDER BY salary) FROM empsalary;# Here the sum is taken from the first (lowest) salary up through the current one, including any duplicates of the current one.
	-Window functions are permitted only in the SELECT list and the ORDER BY clause of the query. They are forbidden elsewhere, such as in GROUP BY, HAVING and WHERE clauses. This is because they logically execute after the processing of those clauses.
	-If there is a need to filter or group rows after the window calculations are performed, you can use a sub-select.
	-SELECT sum(salary) OVER w, avg(salary) OVER w #when we need same over clause at multi places
	  FROM empsalary
  	 WINDOW w AS (PARTITION BY depname ORDER BY salary DESC);
	-The WINDOW clause, if included, should always come after the WHERE clause.
=>When we perform an aggregate function with limit in SQL query aggregate is performed on all rows not just limited ones.
->The more queries running concurrently on a database, the more the database must process at a given time and the slower everything will run. It can be especially bad if others are running particularly resource-intensive queries that fulfill some of the above criteria.

===>To increase query speed:
	-Always try to filter or reduce number of rows before doing join.
	-Use EXISTS instead of IN as IN would scan all rows.
	-Use join if possible instead of sub query as joins(even for self join) are optimized by DB's.
	-Use window functions over joins if possible as they scan table only once.

->Unique CONSTRAINT:
	-SQL Server: Only one NULL allowed unless you use a filtered index.
	-PostgreSQL / Oracle / MySQL: Multiple NULLs allowed because NULL <> NULL.

->Flush: Sends the data to DBMS, Making changes active in the database session but not yet permanent. It can still be rolled back.
	-Flushing makes updates visible to only current session/transaction.
->Using ID(int) vs UUID in table as primary key:
	-As some DB's create default primary index on primary key using id with auto increment maintains insertion order. While UUID being random creates randomized order for records.
		-Helps to retrieve recent records, records inorder from latest to oldest faster. 
		-This also makes writes slower for UUID. As random uuid forces record to insert in random page that cause index fragmentation which can lead to heavy page split.
	-For Sharded table:
		-Using Id's need central system if we need unique id's across diff sharded tables. While UUID is always different irrespective of table.
	-Storage:
		-id 4 to 8 bytes.
		-UUID 16 bytes(36 chars). Consumes RAM when needed.
	=Sol'n: Use Time ordered unique identifiers(UUIDv7 or ULID).
